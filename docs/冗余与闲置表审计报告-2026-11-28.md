## 0. 结论摘要

工程主体是健康的：**前端 105 个 `.vue` 组件零死文件**、`TODO`/`@ts-ignore`/注释掉的大段旧代码均为 0，仓库 `.gitignore` 覆盖了构建产物与日志。冗余集中在三个方向：

1. **数据库有一整批「建了但没接」的表**：69 张业务表里有 **17 张（24.6%）在业务链路上没有任何读写**，全部由 V3/V5/V6/V7/V9 早期迁移建立，此后再无代码触碰。
2. **两个功能用进程内 Map 顶替了已经建好的表**：库存盘点、客户改派日志 —— 表是空的，数据只在内存，**应用重启即丢失**。这是本次审计唯一的**数据正确性风险**（P0）。
3. **代码侧冗余以「只增不减」为主**：41 个前端零调用 API、3 个可直接清理的死端点、2 个已停用的仓储实现、4 个死类/注解、41 组字段完全相同的 DTO 孪生、3 端重复的 4 组工具、`axios` 三处重复声明、以及「起了 Redis 容器但代码零使用」的部署配置。

反过来说，代码卫生面很干净：**0 处 `@Deprecated`、0 处 `TODO/FIXME`、0 处 `System.out.println`、0 处 `printStackTrace`、0 处注释掉的旧代码**，`service/interface` 里也没有孤儿接口。

## 1. 核查方法（可复核）

结论不是靠「看起来没用」得出的，每一项都有机械判据：

| 维度 | 判据 |
| --- | --- |
| 表是否被使用 | 表名在 `server/src/main/java` 全文出现次数（`grep -w`），并结合 `@TableName` 实体数、表内实际行数三者交叉判断 |
| 列是否被使用 | 列名（下划线）与驼峰形式在 `server/src/main/java` 全文的出现次数；**排除** `id/name/status/type/created_at` 等 35 个通用列；含 `SELECT *` 的表另作标注（该表列级判定不可靠，本次未据此定罪） |
| 索引是否冗余 | `information_schema.statistics` 全量导出，两两比对列组合，识别「完全相同」与「是复合索引最左前缀」两类 |
| 类是否死代码 | 类名在 `main` 与 `test` 中分别统计引用次数；带 `@Service/@Repository/@Controller/@Mapper/@Configuration` 等容器注解的排除（靠容器生效）；**统计结果必须再用「限定用法」反查一遍**（`类名.` 形式的实际调用），因为「只 import 未使用」也会被计入引用 |
| 前端 API 是否死 | `src/api/*.ts` 的导出函数在 `views / components / stores / composables / layout` 中的调用点计数（`api` 目录内部互调不计） |

> 说明：`SELECT *` 共 65 处，集中在 chat、order、product 等 23 张表。这些表的列级判定一律不下结论，避免把「被 `*` 带出来的列」误报成闲置。

## 2. P0：用内存顶替已建表的两个功能

这是本次审计最需要处理的部分 —— 不是「多了一张表」，而是**功能实际不可持久化**。

### 2.1 库存盘点（`stock_check` / `stock_check_item`）

| 证据 | 内容 |
| --- | --- |
| 表状态 | 两表均 **0 行**，全仓仅出现在注释里（`替换 V5 的 stock_check / stock_check_item`），无 Mapper、无 PO |
| 实际实现 | `server/.../stock/repository/impl/InMemoryStockCheckRepository.java` —— `ConcurrentHashMap<String, StockCheck>`，类注释自述「进程内适配器；接真库时映射 V5 的 stock_check / stock_check_item」 |
| 唯一实现 | `StockCheckRepository` 接口只有这一个实现，`StockCheckUseCase` 直接注入它 |
| 后果 | 盘点单在应用重启后全部丢失；多实例部署时各实例看到不同的盘点单 |

### 2.2 客户改派日志（`customer_owner_log`）

| 证据 | 内容 |
| --- | --- |
| 表状态 | **0 行**，全仓 1 处引用，且引用本身就是注释 |
| 实际实现 | `server/.../customer/repository/impl/InMemoryTransferLogRepository.java`，注释「进程内适配器；接真库时映射 V3 的 customer_owner_log」 |
| 后果 | 管理端「改派归属」的历史记录重启即失，与「操作流水可追溯」的审计要求冲突 |

> 注：改派的**当前归属**已落在 `customer` 表（`CustomerOperationService.transfer`），丢的只是历史日志；但盘点单是整单丢失，严重度更高。

### 2.3 同源残留：两个已停用但未删除的仓储实现

| 类 | 停用证据 | 判断 |
| --- | --- | --- |
| `customize/repository/impl/InMemoryCustomizeRepository.java` | 类注释「Phase 10 起不再注册为 Bean」；同接口已有 `DbCustomizeRepository` | 死代码（生产 0 引用、测试 0 引用） |

### 2.4 一处已被项目自己记录在案的同类问题

`customer/service/CustomerOperationService.java` 的类注释写得很清楚：

### 4.3 结构性观察

- **0 个外键、0 个视图、0 个存储过程、0 个触发器** —— 完整性全靠应用层。这是既定架构选择（便于分库），不算缺陷，但意味着「删表」不会因为外键依赖而失败，清理成本较低。
- **软删机制是统一的、在用**：19 张表有 `deleted` 列，15 个 Mapper 里共 17 条 `UPDATE ... SET deleted = 1` 批量软删语句；当前有数据的 16 张表 `deleted` 全为 0 只是「还没人删过」，不是死列。唯一不统一的是 `@TableLogic` 只有 3 个 PO 用（`ProductPO`、`FlashSaleActivityPO`、`SysStaffPO`），其余走手写 SQL —— 口径双轨，建议后续统一。
- **审计日志无清理策略**：`sys_operation_log` 已 976 行、跨度 20 天（2026-11-08 ~ 11-28），`job` 包里**没有**对应的归档/清理任务。按当前增速，一年量级会到十万行以上。
