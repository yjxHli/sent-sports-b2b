## 2. 维度一：潜在隐患与代码缺陷

### 2.1 P0-01 · 管理端只读接口对匿名完全开放（实测）

**结论**：`PermissionInterceptor` 的默认策略是「没写 `@RequirePerm` 就放行」，且该判断发生在「是否管理员」之前，因此 **`/api/admin/**` 下所有未注解的接口，任何人不带令牌都能调**。

**证据链**：

| 环节 | 位置 | 内容 |
| --- | --- | --- |
| 默认放行 | `common/interceptor/PermissionInterceptor.java:41` | `if (required == null \|\| required.value().length == 0) return true;` |
| 管理员校验在其后 | 同文件 `:48-56` | 仅当存在注解时才判 `isAdmin()` |
| 匿名直通 | `auth/filter/AuthFilter.java:64-67` | 无 `Authorization` 头 → `chain.doFilter` 继续 |
| 免注解接口清单 | 22 个 GET（见下） | 全部无 `@RequirePerm` |

**亲测复现（匿名、无任何请求头）**：

```
GET /api/admin/orders?page=1&size=2
→ {"code":0,...,"total":"280"}                       # 全量订单
GET /api/admin/customers?page=1&size=1
→ {"code":0,...}                                      # 客户列表
GET /api/admin/customers/92234
→ {"code":0,...,"phone":"1390...."}                   # 客户姓名 + 手机号
GET /api/admin/refunds?page=1&size=1   → code 0        # 全量退款单
GET /api/admin/chat/sessions?page=1&size=1 → code 0    # 全量会话（含 customerId/staffId）
GET /api/admin/custom-orders?page=1&size=1 → code 0
GET /api/admin/stock/flows?page=1&size=1 → code 0      # 库存流水
```

**受影响接口（22 个均无权限注解）**：其中 **9 个已实测匿名返回 200 真实数据**（订单/客户/退款/会话/定制单/库存流水/商品/库存台账），5 个财务读接口因 P0-06 的 50001 无法出数、但同样不设防，其余 8 个方法结构完全同构（可直接按同一机制推断）。

| 控制器 | 行号 | 实测 |
| --- | --- | --- |
| `order/controller/admin/AdminOrderController.java` | `39` (list)、`47` (detail)、`57` (customerOrders) | list ✅ 200 |
| `finance/controller/admin/AdminFinanceController.java` | `86` (receivables)、`97` (invoices)、`124` (invoicePdf)、`145` (contracts)、`155` (paymentRecords) | 50001（见 P0-06） |
| `customer/controller/admin/AdminCustomerController.java` | `42` (list)、`50` (detail) | ✅ 200（含手机号） |
| `chat/controller/admin/AdminChatController.java` | `69`、`78`、`83`、`92` | sessions ✅ 200 |
| `customize/controller/admin/AdminCustomController.java` | `49`、`55` | list ✅ 200 |
| `refund/controller/admin/AdminRefundController.java` | `43`、`56` | list ✅ 200 |
| `product/controller/admin/AdminProductController.java` | `36` | ✅ 200 |
| `stock/controller/admin/AdminStockController.java` | `59`、`66` | ✅ 200 |
| `system/controller/admin/AdminMeController.java` | `29`（`/me` 自身信息，可接受但应要求登录） | 未抽检 |

**影响**：PII（姓名/手机号/地址）、金额、成本价、库存、会话内容全部对外可达；属于「未授权访问」级别，一旦公网部署即等同数据泄露。

**建议**（两层防御，缺一不可）：
1. **改默认**：`PermissionInterceptor` 对 `URI.startsWith("/api/admin/")` 且无注解时**默认拒绝**（40301），只放行显式标注的公开端点。这一条能一次性兜住所有「忘记注解」。
2. **补显式权限点**：为上述读接口补 `xxx:view`（见 P1-03），并同步登记到 `sys_permission`。

### 2.2 P0-02 · 订单详情匿名可读 + 取消/确认收货无归属校验

| 端点 | 位置 | 缺陷 |
| --- | --- | --- |
| `GET /api/orders/{orderNo}` | `order/controller/OrderController.java:85-88` | 无 `@RequirePerm`、不读 `CurrentUser`；`OrderQueryServiceImpl.getDetail()` (`:102-120`) 只按单号查，不过滤 `customer_id` |
| `POST /api/orders/{orderNo}/cancel` | 同文件 `:90-95` | 有 `@RequirePerm("order:cancel")`（=仅要求登录），但 `CancelOrderUseCase.cancel()` (`:35-53`) **完全不校验归属** |
| `POST /api/orders/{orderNo}/confirm` | 同文件 `:97-108` | 同上，`ConfirmReceiptCmd` 只有 `orderNo` |

**实测**（匿名）：`GET /api/orders/SO20261128959034` → `code:0`，返回完整订单（收货人、电话、地址快照、金额、支付状态）。

**影响**：
- 详情：任意人凭单号读他人订单（单号可预测：`SO+日期+序列`，见 `IdGen`），PII 泄露。
- 取消：任意**登录客户**可取消他人的 `WAIT_PAY` 订单 → 释放他人预占库存、打乱他人交易，属可反复触发的业务破坏。
- 对比参照：`RefundController` 做得对——`requireUser(user)` (`:96-99`) + `detail(refundNo, user)` 按 `customerId` 过滤，说明这是**单点遗漏而非设计取舍**。

**建议**：`OrderQueryService.getDetail(orderNo, viewer)` 增加 `viewer` 参数，非管理员时强制 `order.customerId == viewer.userId()`；取消/确认收货在用例入口做同样断言（或用例签名改为 `(orderNo, customerId)`）。

### 2.3 P0-03 · 会员/授信按 `customerId` 参数横向越权（实测）

**证据**：`member/controller/MemberController.java:38-63` 四个只读接口都接收可选 `customerId`，解析逻辑在 `:74-82`：

```java
if (customerId != null && customerId > 0L) return customerId;      // ← 任何人都能指定
if (user != null && CurrentUser.AUD_USER.equals(user.aud())) return user.userId();
return CURRENT_USER_PLACEHOLDER;
```

**实测**（客户 9002 的令牌）：`GET /api/member/points?customerId=92234` → `{"code":0,"data":{"customerId":"92234","availablePoints":"0"}}`；`/api/member/credit?customerId=92234` 同样返回他人授信额度与应收。

**影响**：积分、授信额度、应收账款、专属商品价格属于经营敏感数据；且解析顺序把「显式传参」放在「令牌身份」之前，等于把鉴权交给了前端。

**建议**：显式 `customerId` **仅在 `user.isAdmin()` 时生效**；用户端一律以令牌 `sub` 为准，并在用例层再校验一次（双保险）。注释里「都没有时退回 0，不会误读别人的数据」的表述与实现不符，需一并修正。

### 2.4 P0-04 · 聊天：发送方可伪造 + 会话内容无归属校验（实测）

| 缺陷 | 位置 | 说明 |
| --- | --- | --- |
| `senderType` 由请求体决定 | `chat/dto/ChatDtos.java:32-36`（`SendCmd.senderType`）；`chat/controller/ChatController.java:81-91` 直接透传 | 客户可发 `senderType=STAFF` / `SYSTEM`，伪造客服口径或系统通知 |
| 操作人恒为 0 | 同文件 `:39` `CURRENT_USER_PLACEHOLDER = 0L` | 审计日志无法定位真实发送者 |
| WS 与 REST 口径不一致 | `chat/ws/ChatWebSocketHandler.java:192` `SenderType senderType = fromCustomer ? CUSTOMER : STAFF;` | **WS 按连接身份归一，REST 信任报文** → 断掉 WS 走 REST 即可绕过 |
| 会话消息可匿名读 | `ChatController.java:92-98` `history(sessionId, afterSeq)` | 无 `@RequirePerm`、无归属校验，数字会话号可枚举 |

**实测**：匿名 `GET /api/chat/sessions/1/messages` → `{"code":0,"data":[]}`（可读，只是该会话为空）。

**建议**：`SendMessageUseCase.send()` 入口按 `CurrentUser.aud()` 强制覆写 `senderType`（用户端只允许 `CUSTOMER`，客服端只允许 `STAFF`/`SYSTEM`），`operatorId` 传真实 userId；`history`/`queue`/`read` 增加「会话属于当前客户或接待坐席」校验。

**附带**：前端注释 `web-user/src/composables/useChatSocket.ts:9-10` 明确写着「落库 SenderType 由后端按连接身份写 CUSTOMER，**不信任报文里的 senderType**」——文档说了，REST 没做。

### 2.5 P0-05 · 库存台账「绝对值覆盖写」导致丢更新，可绕过防超卖

**主链路是好的**：`StockMapper.lockStock()` (`stock/mapper/StockMapper.java:38-41`) 用条件更新在行锁内判定可用量，注释与实现一致，`20 线程抢 1 件只命中 1 次`。

**旁路有洞**：`StockRepositoryImpl.save()`（`stock/repository/StockRepositoryImpl.java:101-113`）先**无锁读**、再由调用方改、最后 `updateLedger()` **四列全量覆盖**：

```java
SkuStockPO before = stockMapper.selectBySkuId(skuId);          // 101-104，普通快照读
stockMapper.updateLedger(skuId, item.getPhysicalQty(), item.getLockedQty(), ...);  // 105-106
```

而 `StockMapper.updateLedger()`（`stock/mapper/StockMapper.java:63-70`）的 SQL **没有 `version` 条件、没有 `FOR UPDATE`**：

```sql
UPDATE sku_stock SET physical_qty=#{...}, locked_qty=#{...}, pending_qty=#{...}, frozen_qty=#{...},
       version = version + 1 WHERE sku_id = #{skuId}
```

**并发窗口**（可超卖）：

```
T1 入库(管理员)      : SELECT → physical=100, locked=5
T2 客户下单           : UPDATE locked_qty = locked_qty + 2  (提交，locked=7)
T1                   : UPDATE ... locked_qty = 5           ← 丢掉了 T2 的 2 件预占
```

**触发点**（均为 `@UseCase` 事务内）：`stock/service/InboundUseCase.java:45-52`（入库）、`LossUseCase.java`（报损）、`StockCheckUseCase.java:81-90`（盘点调账）、`service/impl/SkuStockInitServiceImpl.java:32`。

**影响**：可用量被高估 → 超卖；`stock_flow` 与台账对不上（流水记了 LOCK，台账没有）。

**建议**（任选，推荐 1+2）：
1. `save()` 改用已有的 `selectBySkuIdForUpdate()`（`StockMapper.java:82-83`，目前**无人调用**）做行锁读；
2. `updateLedger` 增加 `AND version = #{version}`，影响 0 行抛 `STATE_CONFLICT`；
3. 长期：入库/报损/盘点全部改走 `adjustPhysical`（已有，原子 `+delta`），只有盘点差异需要覆盖时才用锁读。

## 5. 维度四：架构设计一致性

### 5.1 分层（✅ 达标）

`ArchitectureTest` 5 条规则全绿，且规则设计到位：

| 规则 | 位置 | 评价 |
| --- | --- | --- |
| controller 不依赖 mapper | `ArchitectureTest:47-52` | ✅ |
| domain 不带 Spring 注解 | `:56-66` | ✅ 抽查 `Order`/`StockItem`/`RefundOrder` 均为纯 POJO |
| common 不依赖业务模块 | `:70-75` | ✅ `PermissionChecker`/`DataScopeResolver` 用端口倒置，是范本 |
| 跨模块只走 service | `:79-89` | ✅ 抽查 `CreateOrderUseCase` 全部门面注入 |
| 订单状态只能 domain 改 | `:93-98` | ✅（**但只有 Order 有这条守护**） |

**唯一的边界妥协**（已在代码里显式记录，可接受）：`StockMapper.selectLockedLinesByOrderNo`（`stock/mapper/StockMapper.java:77-79`）直读 `order_item` 表，注释说明是为避免 `order→stock→order` 循环依赖。属**合理越界**，但建议改为 `order` 模块提供一个只读 `OrderLineQuery` 端口，把这行 SQL 挪回 `order` 模块——ArchUnit 抓不到 mapper 内嵌 SQL 的跨表读，这是规则盲区。

### 5.2 状态机（🟡 Order/Custom 好，Refund/Pay 有缺口）

| 域 | 状态机 | 是否有绕过路径 | 结论 |
| --- | --- | --- | --- |
| 订单 | `order/domain/OrderStateMachine.java`（迁移表 + `transit()`）+ ArchUnit 禁用 `setStatus` | 无 | ✅ 范本 |
| 定制 | `customize/domain/CustomStateMachine.java`，`CustomOrder.transit()` (`:96`) 是 domain 层唯一入口 | 无（domain 无 `setStatus`） | ✅ |
| 退款 | `refund/domain/RefundStateMachine.java` 存在，但 `RefundOrder.setStatus()` (`:79`) **public 且无调用**；`RefundServiceImpl:60-69` 直接构造 `REFUNDING` 态；`:71-88` 用 SQL 直插 `REFUNDED` 态 | **有 2 条** | 🟠 建议：删 public setter；`createCloseRefund`/`createOnlyRefund` 改为聚合构造 + `transit`；再加一条 ArchUnit（照抄 Order 那条） |
| 支付 | `order/domain/PayStateMachine.java` + `PaymentTxn.markFailed/markClosed` **均为死方法** | 失败/关闭态从不落库 | 🟡 要么补「失败回调」链路，要么删掉这两个态与枚举值，避免「有态无路」 |

### 5.3 幂等（🔴 断层）

| 层面 | 实现 | 结论 |
| --- | --- | --- |
| 订单创建 | DB 唯一键 `uk_order_idem`（`OrderRepositoryImpl:67-72` 捕获 `DuplicateKeyException` → `DUPLICATE_PROCESSING`） | ✅ 唯一真正生效的幂等 |
| 库存释放 | `uk_flow_biz(biz_type,biz_no,sku_id)` + 捕获重复键（`StockRepositoryImpl:69-80`） | ✅ 设计精巧 |
| 支付/退款/发货/回款 | 前端全部发送 `Idempotency-Key`，后端 `@Idempotent` **0 处** | 🔴 **头发出去了，服务端不看** |
| 幂等存储 | `InMemoryIdempotencyStore` + 惰性过期（`:59-69`），**无后台清理、无容量上限** | 🟠 即使启用也会缓慢泄漏；多实例部署跨节点不幂等 |

**结论**：幂等分成「DB 唯一键（真）」和「拦截器（假）」两套，前者覆盖订单/库存释放，后者覆盖 0 个接口。这不是「没做幂等」，而是**两套机制并存且互相不知道对方存在**——架构上比完全没做更危险，因为它给了「已防重」的错觉。

### 5.4 防超卖（🟡 主链路达标，旁路破防）

| 链路 | 机制 | 判定 |
| --- | --- | --- |
| 下单预占 | `UPDATE ... WHERE available >= qty`（`StockMapper:38-41`） | ✅ 行锁内判定，可抗并发 |
| 超时释放 | `uk_flow_biz` 幂等 + `GREATEST(locked-qty,0)` 下限保护 | ✅（`GREATEST` 会掩盖「多释放」的真实 bug，建议加 warn 日志） |
| 出库 | `shipStock` 带 `locked>=qty AND physical>=qty` 双条件 | ✅ |
| 入库/报损/盘点 | `save()` 绝对值覆盖 + 无锁读 | 🔴 **破防**，见 P0-05 |
| 订单头并发 | `updateHeader ... WHERE version = #{version}`（`OrderMapper:203-205`） | ✅ 手工乐观锁（注意：`OptimisticLockerInnerInterceptor` 已注册但全仓无 `@Version`，实际未启用——**不是 bug，但要防止后人误以为插件在生效**） |

### 5.5 数据范围（🔴 口径不一）

只有 report 域把 `@DataScope` 真正落到 SQL（5 个方法，含真实调用）；order 域唯一那条挂在零调用的 `selectForAdminList` 上；customer/customize/refund/chat 四个域**注释写了、代码没做**（P1-04）。根因是「默认不过滤」+「注解可选」，与 P0-01 是同一类设计缺陷：**安全机制默认关闭**。

### 5.6 内存 vs 真库（🟡 叙事冲突）

代码注释反复强调「真库」「V69 清理闲置表」，但仍有 6 个 `InMemory*` 仓储是**生产生效 Bean**：

| 实现 | 生效为唯一实现? | 影响 |
| --- | --- | --- |
| `InMemoryAgentPresenceRepository` | 是 | 坐席状态重启丢失、多实例不一致、`staff_presence` 表空转（M-4） |
| `InMemoryCreditLineRepository` | 是 | `CreditGrantUseCase` 双写（内存 + `enterprise_profile`），但返回给前端的 `available()` 来自内存（`used=0`）→ 重启后「可用额度」虚高（真实校验已走 `CreditFacadeImpl` 读 DB，故**不产生资损**，但会误导运营） |
| `InMemoryPaymentReverseRepository` | 是 | 冲销记录重启丢失（`reverse` 是资金动作，建议核实是否另有 DB 落点） |
| `InMemoryLogoutTokenRepository` / `InMemoryRefreshTokenStore` | 是 | 登出/刷新令牌重启失效（可接受，属会话语义） |
| `InMemorySmsCodeStore` | 是 | 验证码重启失效（可接受） |
| `InMemoryIdempotencyStore` / `InMemoryRateLimiter` / `InMemoryConfirmTokenStore` | 是 | 多实例部署时全部失效 |

**建议**：把「允许内存」的（会话/验证码/限流）与「必须持久」的（坐席状态、授信占用、冲销记录）显式分档，并在类注释标明 `@implNote 仅单实例`，避免后续误判。
